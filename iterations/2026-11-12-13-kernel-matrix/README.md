## 固定范围与实现

`NtfsKernelMatrix` 固定21个对象、每对象Initial/Reopened/Flushed三个时点，共63次请求，低于24对象/96次预算。A为三类型×8/24/64字符名称（9对象）；B为同类型短/长名分别增加固定8字符别名（6）；C为同类型短/长名增加固定meta命名流（6）。类型为普通、LZNT1压缩、稀疏；同类型默认流内容/EOF固定，目录与创建次序明确，B/C不叠加，特性设置失败不伪通过。默认EOF、实际类型、可见硬链接数以及前后Native上下文逐次核对。不修改主机8.3策略；只有解码成功才报告名称数。

脚本新增 `-KernelDiagnostics`，模式在fixture与卷marker绑定。父入口仍先检查随机workspace/nonce、镜像文件、虚拟设备extents、分区范围、NTFS3.1与512/4096几何。每次读取校验外层返回槽/长度、正文序列及Native前后完整身份、大小、链接数、时间与无写者证据，再交给原严格解码器；基础设施错误中止，严格解码失败则继续收集。

`CaptureKernel` 将IOCTL外层引用/长度/返回量和已核对的Native上下文存入严格schema2清单，正文原样保存、SHA-256绑定，旧schema1仍严格兼容。离线只能证明保存内容自洽与重现结果，不能再次证明过去的卷稳定性。数量、体积、JSON字段/重复字段、路径和重解析守卫保留。

两次诊断分别见 diagnostic-first.json / diagnostic-final.json。第一次之后补充空会话清理失败不覆盖已完成摘要的受控状态及纯测试，最终代码重新运行后得到相同结果：

两次27条失败都来自64字符名称组的9个对象（三类型，含A/B/C）及三个时点；8/24字符组没有失败。通过组记录使用长度最大504，失败组最小576，失败尾字均P0/R1/S2。名称/使用长度与失败相关，但不能据此证明跨扇区、缓存或其他原因；关闭、重开及刷新没有消除这些失败，也不能称为磁盘损坏。

每次按固定顺序保留前6个失败观察（普通长名和压缩长名的三个时点）；矩阵摘要覆盖全部63次，原始样本不是全部失败类型的逐条副本。首批在卸载后独立进程6条全部匹配，按清单/nonce/哈希核验后清理，再运行最终矩阵，避免同时超过总6条上限。最终6条均Source=KernelIoctl，在卸载后独立重放6匹配/0失配，受控证明见 replay-summary.json。重现的原结果是FixupMismatch，**Matching不等于解码通过**。

最终约9.5KiB的6条原始正文/绑定清单作为下一步研究样本仅保留本机ignored artifacts，不归档原始内容、完整身份、路径或哈希；三次VHD镜像均已卸载删除。研究所需样本保留至下一阶段使用完毕后按归属清理，不删除未知文件。没有个人卷扫描、系统日志设置变化或持久后台采集。
