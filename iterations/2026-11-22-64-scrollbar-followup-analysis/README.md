# C64：新视频的滚动残留分析

2026-11-22，基线`eee2104fc03584bddf9f1c0a202d9c78c4ccaace`。用户提供扩展视频，要求先结合三次修复经历分析；本轮没有修改C#、重建、换程序、录屏或系统设置，阶段三仍未实施。

## 已看到的事实

约22.54秒视频共有1238个解码视频帧。约2.33秒和18.03秒可见底部同名行重复绘出、固定背景横向接缝。停止后多能恢复，变化常只在少量连续录制帧中出现；不能只看停止后的截图。列表内容背景和细轨道背景并未始终呈现同一位置的连贯底图。尚无证据表明扫描数据被修改或真的增加重复文件，当前证据指向显示残留。

在本次抽帧及轨道边缘观察中，没有看到旧版那样明显的大面积系统灰轨道重新持续铺满；滑块仍有移动/松手状态变化，不能据此认定滑块所有连续行为已正确。视频缺少输入消息和系统偏好记录，不能仅凭录制节奏断定每段采用了实时还是延迟提交，也不将轨道色差全归为同一原因。

## 已核对的代码与推断

`src/UI/ScrollbarPointerTracking.cs`的Emit直接raise(bar,args)，没有包入`WallpaperGrid.PerformBufferedScroll`。`Wallpaper.cs`现有保护覆盖滚轮、部分键盘和WM_H/VSCROLL；直接托管事件不会自动走这段消息分支。官方.NET10 DataGridView.ScrollRows先更新条值，执行ScrollWindow搬移客户区已有像素，之后才触发OnScroll。本项目OnScroll中Invalidate/Update是事后修补，无法保证从搬移到补画之间不显示旧背景。

所以首要原因候选是新指针路径绕过原固定底图滚动保护，叠加列表和原生子条各自发布的时序；代码缺口可直接核对，与视频吻合。**尚未做开关这一边界的同条件因果对照，不能称为已证明唯一根因。** 滚轮本身有保护，也须在对照中单独检查，不能假定只补指针就覆盖全部问题。

## 前几次为何没有一次解决

前面依次处理了系统灰轨道直接绘制、抑制原生重绘后滑块位置/长度缓存未同步、延迟模式松手释放前的旧值。它们是不同缺陷，修正有实际价值；但本轮检查暴露整体呈现仍漏了一层。指针专项主要取轨道边缘/数值，原列表回归等待后又Update，少量GDI样本也不是连续屏幕验收。测试通过未证明整块列表中间画面正确，这一验收遗漏需修正。用户早先接受的几何结果按当时范围保留，不删改冻结C63证据；当前缺陷重新打开。

## 建议的下一步，尚未实施

先用自有有纹理背景和真实MainForm列表，固定快速往返拖条、缓慢滚轮、反向、松手及失捕获，补出背景随内容搬移/重复行反例；同时观察列表内容、滑块、轨道三块表面。随后仅统一滚动提交与最终发布边界，保持背景固定、内容滚动、条几何同步，不靠新增事后全窗强刷。需分别核实时和延迟系统偏好，不修改系统设置，不能只检查bar.Value而不检查实际列表位置。用户确认后再实施、展示真实正常版。
