# 2026-11-01 / 01：建立项目工作规则

## 本轮范围

根据用户提供的自然语言需求补全根目录 `AGENTS.md`，将其作为 AsukaLens 后续迭代、验收、提交和发布的项目约定。本轮不修改应用代码、视觉界面、扫描算法或构建脚本，不实施路线图，不进行版本升级、打包或正式发布。

原始 `AGENTS.md` 已存在但为空（0 字节）；本轮修改这一文件，新增本轮记录、恢复补丁及文件校验清单。完整源码首次上传和本地 Git 初始化不在本轮范围内。

## 需求覆盖与决策

| 用户要求 | 规则中的落实 |
| --- | --- |
| 1. 保留七项功能，优化六个方向 | 明确七项保留功能；分别记录扫描策略、进度与果冻动效、可靠增量、组件设计、背景裁切与取色适配、三类日志的目标和验收边界。 |
| 2. 较大改动先给方案 | 列明哪些改动先给方向、影响及验收方法；选定后连续实施，不为日常步骤重复询问。 |
| 3. 只在正式版本打包 | 区分普通构建、验证、提交与正式打包；当前打包脚本不用于普通迭代的无条件检查。 |
| 4. 指定仓库及 main | 使用用户提供的 GitHub 仓库地址，main 为目标分支；先检查历史，不覆盖并发变更。 |
| 5. 验证后自动提交上传 | 本轮必要文件通过检查后自动提交；只暂存必要内容，不强推、不暴露身份隐私。 |
| 6. 正式 Release 规范 | 统一 vX.X.X；便携 ZIP、真正的 EXE 安装器、源码 ZIP 与 tar.gz；可用性验证、校验值、版本说明和每版远程快照。 |
| 7. 美观的中英文 README | 约定 README.md 与 README.en.md；包含预览、环境、功能、使用、源码构建、路线图、目录结构；视觉方向先选择。 |
| 8. 隐私优先 | 日志、背景、截图、归档、提交与发布均不得含私密数据；默认本地、必要记录、脱敏导出。 |
| 9. 每轮清理冗余 | 清理临时文件、夹具和重复产物，同时保留必要依赖、迭代证据与远程历史快照。 |
| 10. 清晰目录 | 定义简单的源码、测试、资源、脚本、文档与迭代目录方向；迁移先给方案，不为排版建立空层级。 |
| 11. 健壮性、完整性审查及关键文件归档 | 每轮记录验收、审查、验证和未完成项；统一归档到 iterations/，以补丁和校验清单保留关键文件。 |

进度百分比必须有真实依据，未知总量时允许清楚标注的估算或不确定进度，禁止按时间伪造；减少增量核验须有连续可信的变化证据，失效时仍应保证正确恢复。不能承诺所有目录下高速模式必然最快，也不能用人为延迟制造表面差距。

正式发布文件示例为 `AsukaLens vX.X.X.zip`、`AsukaLens vX.X.X.exe`、`AsukaLens vX.X.X-source.zip` 和 `AsukaLens vX.X.X-source.tar.gz`。`.NET` 的数值版本字段保留对应的纯数字格式。安装器、双语 README 和完整发布流水线当前尚未完成，未将既有软件追认为符合新规范的 Release。

## 审查与验证

- 检查 11 项需求的覆盖、目标与现状的区分、较大改动的决策边界，以及普通迭代和正式发布的区别。
- 检查自动上传与隐私、远程版本保留与本地清理、对外版本格式与技术版本字段之间没有互相冲突。
- 检查命令确实对应现有项目和测试入口；未修改命令或脚本来假装已经实现新的发布机制。
- 检查文件未包含本机用户名、真实扫描路径、文件清单、私人日志、凭据或私人邮箱；仓库地址与参考链接均为用户提供的公开项。
- 校验关键文件及补丁的 SHA-256；在隔离的空白文件基线上检查并应用补丁，确认恢复结果一致。首次恢复发现本机 Git 自动转换换行造成字节差异，改用单次命令的 `core.autocrlf=false` 保持档案 LF，不修改全局配置。
- 本轮仅改文档，不运行应用测试、磁盘基准或构建，不将历史测试数量当成本轮实测结果。

## 关键文件与恢复

- 生效规则：项目根目录 `AGENTS.md`。
- 历史证据：本目录 `changes.patch`；校验清单：`files.json`。
- 本轮基线是项目根目录中一个空白的 `AGENTS.md`。在独立目录准备同名空文件，再执行 `git -c core.autocrlf=false apply changes.patch`（使用补丁的实际路径），可恢复本轮规则文件；不要在已修改的真实项目上直接覆盖恢复。
- GitHub main 的提交记录提供本轮上传的提交关联；本轮不归档软件二进制、用户背景或运行日志。
