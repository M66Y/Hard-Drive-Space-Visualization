# 路线图第 1 轮：驻留分配补查与成本

日期：2026-11-12。基线：`6242e71b9f3c072f0446e3cdfd5e5bcccc28daad`。用户要求即刻开始计划第 1 轮，并另行同意本轮继续使用已审查的 256 MiB 隔离 VHD 流程。本轮限于普通驻留 DATA 的分配口径、大小来源和小规模补查成本，不实施磁盘活动面板、压缩/稀疏算法、属性拼接、整卷 MFT 读取或产品入口。

## 实现

`NtfsSizeLookup.cs` 仅编入测试项目。输出区分 Record / HandleLookup / Unknown；逻辑大小保留记录来源，分配量只有在两次 NativeStorage 回调的身份、逻辑大小、链接数、修改时间和分配量稳定，且无打开写句柄时才接受。错误不携带原始异常消息，失败保留分配未知。

仅单一 `ResidentAllocation` 原因可进入补查；其他类型明确不支持，不能顺带用句柄结果清除未解决的范围问题。每批单路、无队列、无跨批缓存，最多 4096 个唯一对象；重复身份、同槽不同序列、相同路径不同对象和名称超限均在 I/O 前拒绝。取消前/中会抛出并丢弃部分结果，不承诺打断已进入的同步系统调用。调用方仍须保证范围和输入新鲜度；这不是活跃卷一致性证明。

`NtfsLookupExperiment.cs` 与真实夹具增加 1/7/8/9 等长度及更大文件、驻留硬链接；按唯一对象送入补查，避免将硬链接入口当成多份对象。暖缓存预读和预热后，以 AB/BA 交替 6 轮比较选择性补查与全部对象双读对照，逐项核对结果在计时区间之外。`NativeCalls` 是整个 reader/NativeStorage 回调的次数，不是单个 Win32 调用或物理 I/O；回调耗时同理。

VHD 脚本仅在成功且清理完成时转存严格白名单实验摘要。新增摘要检查拒绝额外字段、错误类型/关系/范围、非有限时间、错误样本顺序或过多示例，防止文件路径等意外进入公开结果。

## 真实夹具结果与限制

两次本轮 VHD 执行都通过，第一次 847 项；补充驻留硬链接后最终 862 项。两次结果均 `detached=true`、`cleanup_completed=true`，见 `live-attempts.json`；镜像、夹具、原始临时摘要与运行日志已清理。

最终普通候选对象 25 个，其中 20 个驻留、5 个直接取值；另有 3 个压缩/稀疏/命名流对象明确排除，不算作直接成功。因此这组人工候选的补查比例为 80%，不是现实软件或整盘分布。

| 指标 | 选择性补查 | 全部对象双读对照 |
| --- | ---: | ---: |
| 每轮 NativeStorage 回调 | 40 | 50 |
| 最终运行 6 轮总耗时中位数（ms） | 1.0389 | 1.8199 |
| 最终运行耗时范围（ms） | 0.9147–2.5846 | 1.1682–2.9575 |

这里的对照是两次句柄稳定检查，不是现有生产扫描器。当前生产完整扫描通常逐入口做一次 NativeStorage 读取，入口数和唯一对象数也不同；不能把 40 对 50 宣称为相对生产扫描节省。实验不含文件创建、MFT 获取、建树、UI 或补查以外的工作，没有冷缓存控制、CPU、峰值内存或物理 I/O 测量。两次运行有明显耗时波动，保留全部样本，不据此承诺加速比例。

本轮普通驻留示例中，1 字节句柄分配为 8、9 为 16、17 为 24，说明将独立数据簇 0 直接当作现有分配口径不成立。尽管当前例子呈现 8 字节对齐，不将一次主机/夹具观察写成通用 NTFS 公式；本轮使用经身份校验的句柄来源。其他版本、几何、改写/缩小和复杂属性布局仍需验证。

## 后续与交付

普通驻留补查已可正确工作，但高补查比例及双读成本仍可能抵消批量读取收益。下一轮先评估更低成本且可验证的驻留大小来源，或有连续变化证据的稳定性方案，再分别处理其他特殊类型。尚不能据此进入正式高速扫描或宣称 NTFS-01 全部完成。

本轮源码、文档、精选白名单摘要与补丁归档；未打包、创建标签或发布版本，生产扫描器未接入原型。`changes.patch` 不包含自身，文件与 SHA-256 清单见 `files.json`，补丁反向适用检查用于验证可恢复性。
