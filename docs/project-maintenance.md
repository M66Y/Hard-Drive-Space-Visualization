# 项目维护细则

## Git 提交与上传

- 目标仓库：`https://github.com/M66Y/Hard-Drive-Space-Visualization.git`；目标分支：`main`。
- 用户已授权：本轮改动验证通过后自动提交并推送到 `main`，不为普通提交重复请求确认。较大改动的实施仍先遵循方案规则。
- 首次接入先检查本地与远程历史，安全初始化或对齐。暂存前逐项核对范围与隐私；不使用无差别暂存上传个人数据，不覆盖用户未提交的修改。
- 提交应完整、可追溯且说明目的；只包括本轮必要文件。默认不提交编译中间物、软件运行目录、发布二进制包、个人配置或原始日志。发布资产使用 Release 管理。
- 使用用户已配置的非隐私身份或已验证的 GitHub noreply 身份；不得暴露私人邮箱、令牌或凭据。凭据使用凭据管理器或平台连接，不写入文档和脚本。
- 推送前检查远程进展；有并发变更先整合并验证，不强制推送、重写或删除远程历史。分支保护或权限不允许时如实报告并保留本轮成果，不绕过规则或宣称已上传。
- 可以用已授权的 GitHub 连接提交本轮文件；若采用这种方式，明确区分远程已提交与本地 Git 尚未初始化，不宣称已完成整个源代码仓库初始化。

## 双语 README 与公开署名

- 简体中文入口为 `README.md`，英文为 `README.en.md`；顶部互相提供语言切换链接，版本、功能状态、安装步骤和下载地址同步维护。
- 推荐阅读顺序：产品名与一句话定位 → 界面预览与下载入口 → 适用环境 → 功能 → 快速使用 → 从源码构建及运行/安装 → 待优化与开发 → 项目结构树和关键目录。
- 区分“从源码构建运行”和“安装发行包”；当前构建不能产生安装器时，不写成已经支持。计划功能明确标为待开发，不把本文件目标全部勾选完成。
- 视觉参考：MetaGPT 的产品标识、语言入口、徽章与上手层次；Mizuki 的主题表达、预览图和功能分组。取其信息组织方式，不照抄文案、图片或无关技术说明。
  - `https://github.com/FoundationAgents/MetaGPT`
  - `https://github.com/LyraVoid/Mizuki`
- 重要视觉方向或新增优秀参考先展示给用户选择，再统一编写。只展示真实可用的下载、版本与构建状态；不过度堆叠徽章、装饰或大图。
- 截图使用自建演示目录或已脱敏数据，不展示开发者或用户的真实目录、账户、文件清单和日志。图像资源应有说明与替代文字，双语排版保持一致。

## 目录、归档与清理

- 目录名应简单明确。后续组织方向为 `src/`（源码）、`tests/`（测试）、`assets/`（可分发资源）、`scripts/`（构建发布）、`docs/`（说明）、`iterations/`（每轮记录）；根目录保留项目入口、必要配置和中英文 README。
- 这是后续重组方向，不代表这些目录已经存在。目录整体迁移先给方案；迁移后同步项目引用和构建路径，不能为了形式创建空目录或复杂层级。
- 每轮统一归档到 `iterations/YYYY-MM-DD-NN-简短主题/`，至少提供一份 `README.md`，记录需求范围、关键决策、关键文件、功能验收、健壮性审查、实际验证结果、未完成项和清理情况。
- 关键文件的可恢复变更保存为该轮目录内的 `changes.patch`，必要时附精选的脱敏截图、配置样例或小型证据；记录文件清单、SHA-256 和恢复所需基线/提交关联。Git 历史保存完整源码，避免每轮复制整份项目。
- 补丁记录真实基线提交并检查可恢复性，只包含本轮必要文件，不递归包含自己或旧归档。首次建立规则的空白基线只是历史特例。补丁是历史证据，不是另一份生效规则。
- 不归档原始个人日志、凭据、真实扫描结果、用户图片、完整磁盘镜像、编译缓存和重复的大型安装包。开发日志公开内容与本机私有日志必须区分。
- 每次迭代结束清理本轮无用临时文件、测试夹具、中间物和重复产物；保留必要源码、资源、依赖、当前可用软件和精选迭代证据，不把正常依赖误判为冗余。
- 递归删除前核对解析后的绝对路径确实位于目标工作区或本轮创建的临时目录；只清理明确归属本轮或可再生成的文件，排除重解析点和仍在使用的产物，不删除未知用户文件、归档证据及远程快照。
- 保留能力优先依赖版本控制与远程发布快照；归档保持精简。归档增长明显时先报告体积并给整理方案，不默默删除历史或无限堆积。
